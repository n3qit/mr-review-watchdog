# Учёт выходных и праздников: логика и альтернативы

Этот документ описывает, как `mr-review-watchdog` определяет «рабочий
возраст» МР (реализация — [internal/checker/businesstime.go](../internal/checker/businesstime.go),
клиент API — [internal/calendar/client.go](../internal/calendar/client.go)),
почему выбрана именно ленивая приближённая схема, и какой была рассмотренная
альтернатива.

## Задача

`min_age_hours` должен считаться не в астрономических часах с момента
создания МР, а только по часам, попавшим на рабочие дни: время, пришедшееся
на выходные (Сб/Вс) и праздники производственного календаря РФ, в возраст не
засчитывается. Источник данных о праздниках — публичный API
[calendar.kuzyak.in](https://calendar.kuzyak.in).

Релевантные эндпоинты API:

| Эндпоинт | Что возвращает | Стоимость |
|---|---|---|
| `GET /api/calendar/{year}/holidays` | Список праздничных дат за год (`holidays[]`) и предпраздничных сокращённых (`shortDays[]`, они остаются рабочими) | 1 запрос на **год** |
| `GET /api/calendar/{year}/{month}/{day}` | Авторитетный статус конкретной даты: `isWorkingDay`, `isShortDay`, `holiday` — учитывает вообще все особенности календаря, включая переносы | 1 запрос на **дату** |

## Выбранный вариант: приближённая схема по списку праздников

Алгоритм (`internal/checker/businesstime.go`):

1. На старте прогона создаётся `holidayCache` — пустой словарь `год → набор дат`.
2. Для каждого МР, чей возраст нужно посчитать, дата создания и «сейчас»
   переводятся в московское время (`Europe/Moscow`, дата — это то, в каком
   часовом поясе живёт производственный календарь РФ).
3. День считается рабочим, если одновременно:
   - это не суббота и не воскресенье (день недели вычисляется локально,
     без обращения к API);
   - его нет в списке `holidays[]` года, к которому относится дата.
4. Список праздников года запрашивается **лениво** — только когда впервые
   встречается дата из этого года — и **кэшируется** в `holidayCache` на
   время всего прогона. Повторные обращения к датам того же года не делают
   новых HTTP-запросов.
5. Время, попавшее на рабочие дни в диапазоне `[создание МР, сейчас]`,
   суммируется (с учётом частичных суток в начале/конце диапазона) — это и
   есть «рабочий возраст», который сравнивается с `min_age_hours`.

Стоимость: **не более одного HTTP-запроса на встретившийся год за весь
прогон** (обычно 1, максимум 2, если проверка идёт на стыке лет), независимо
от количества репозиториев и МР.

Ошибка получения календаря года — это ошибка уровня конкретного МР (попадает
в `report.Errors`), а не фатальная ошибка всего прогона: не удалось посчитать
возраст одного МР — остальные проверяются как обычно.

### Ограничение приближённой схемы

`holidays[]` не содержит информации о **переносе выходного дня на будний и
обратно** (перенос рабочего дня на субботу/воскресенье, распространённая
практика в РФ) — эти дни в API отдельно нигде не перечислены, узнать про них
можно только через поштучный запрос конкретной даты.

Мы проверили это эмпирически, дёрнув `/api/calendar/{year}/{month}/{day}`
для каждой субботы и воскресенья 2023–2026 годов:

| Год | Даты с переносом (суббота/воскресенье оказались рабочими) |
|---|---|
| 2023 | не найдено |
| 2024 | `2024-11-02`, `2024-12-28` |
| 2025 | `2025-11-01` |
| 2026 | не найдено (на момент проверки) |

Приближённая схема ошибочно считает эти даты нерабочими. Практическое
следствие: если возраст МР целиком укладывается в такое окно, МР может быть
помечен проблемным на **~1 день позже**, чем формально положено. Ошибка
всегда **в одну сторону** — «МР ещё не считается проблемным, хотя мог бы» —
и никогда не приводит к ложному срабатыванию раньше времени. Частота — 0–2
даты в год.

## Рассмотренная альтернатива: точная схема по дате

Вместо списка праздников — для каждой даты в диапазоне
`[создание МР, сейчас]` запрашивать её авторитетный статус через
`GET /api/calendar/{year}/{month}/{day}` (`isWorkingDay`). Это полностью
устраняет ограничение выше: перенесённые рабочие выходные учитываются
корректно, потому что статус даты приходит от источника истины, а не
реконструируется локально.

Стоимость: количество запросов на один МР равно количеству календарных дней
в диапазоне `[создание МР, сейчас]` (не всего года — только фактического
возраста конкретного МР). Для одного протухшего МР это обычно единицы —
низкие десятки запросов; при большом количестве проблемных репозиториев и МР
суммарное число запросов за прогон растёт линейно от суммарного «возраста»
всех проверяемых МР, а не от количества встретившихся лет.

## Почему выбрали приближённую схему

| | Приближённая (список праздников) | Точная (по дате) |
|---|---|---|
| HTTP-запросов за прогон | ~1 на год (обычно 1) | ~1 на календарный день возраста, на **каждый** МР |
| Точность | Не учитывает перенесённые рабочие выходные (0–2 даты/год) | Полная, источник истины |
| Направление ошибки | МР помечается позже положенного, никогда раньше | Ошибок нет |
| Сложность кода | Простой словарь `дата → праздник`, локальная проверка дня недели | Нужен постраничный обход дат с обработкой ошибок на каждую дату |
| Устойчивость к сбоям API | Один сбой = не посчитан возраст МР из одного года | Один сбой на любую дату диапазона = не посчитан возраст МР |

Договорились (см. обсуждение в задаче), что редкость случая (0–2 даты в год)
и однонаправленность ошибки (только «попозже», никогда «пораньше», то есть
это не приводит к ложным уведомлениям) не оправдывают на порядок больший
объём запросов и более сложную логику точной схемы. Если это ограничение
станет ощутимым на практике — переключение возможно локально, в пределах
`internal/checker/businesstime.go` и `internal/calendar`, без изменений
конфигурации или остального пайплайна.
