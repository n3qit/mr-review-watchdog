# ТЗ: tf-mr-check

## 1. Назначение

Утилита `tf-mr-check` проверяет заданный список репозиториев GitLab на наличие merge request'ов (МР), которые открыты более суток и не набрали минимально необходимое количество ревью. Найденные МР публикуются списком в канал Mattermost. Ошибки, возникшие в ходе проверки, публикуются отдельно — реплаем в тред под сообщением со списком проблемных МР.

Бинарник запускается разово (по расписанию — через внешний cron/scheduler), не является демоном.

## 2. Окружение

- Источник МР: GitLab EE v18.7.7-ee, GitLab REST API v4.
- Назначение уведомлений: Mattermost, REST API (`/api/v4/posts`), аутентификация бот-токеном (personal access token бота с правом постить в целевой канал). Incoming Webhook не используется, так как не возвращает ID созданного поста, необходимый для треда.
- Язык реализации: Go.
- Расположение точки входа: `cmd/tf-mr-check/main.go` (единственный бинарник в этом репозитории на данный момент).

## 3. Термины

- **МР (merge request)** — объект GitLab merge request.
- **Draft МР** — МР со значением поля `draft = true` (либо legacy `work_in_progress = true`). Не участвует в проверке.
- **Ревьюер** — пользователь, отличный от автора МР, оставивший по МР хотя бы одно из: approve (GitLab Approvals API), комментарий/обсуждение (Notes/Discussions API), запрос изменений. Считаются уникальные пользователи.
- **Проблемный МР** — открытый, не draft, созданный более `min_age_hours` назад, с количеством уникальных ревьюеров меньше `min_reviewers`.

## 4. Функциональные требования

### 4.1. Получение и фильтрация МР

Для каждого репозитория из конфигурации:

1. Получить все МР в состоянии `opened` (с пагинацией по GitLab API).
2. Исключить draft МР (`draft == true` или `work_in_progress == true`).
3. Исключить МР, у которых `created_at` моложе `min_age_hours` (по умолчанию 24 часа) относительно текущего времени.
4. Для оставшихся МР получить:
   - список approvals (GitLab Approvals API);
   - список notes/discussions, отфильтровав системные заметки (system notes) и заметки автора самого МР.
5. Посчитать объединение уникальных пользователей из approvals и notes (исключая автора МР) — это количество ревьюеров.
6. Если количество ревьюеров < `min_reviewers` (по умолчанию 2) — МР считается проблемным и попадает в отчёт.

### 4.2. Обработка ошибок

- Ошибка при обработке одного репозитория (например, недоступен API, невалидный проект, таймаут) не должна прерывать проверку остальных репозиториев из списка.
- Все ошибки собираются в отдельный список с указанием репозитория (и МР, если применимо) и текста ошибки.
- Ошибки не смешиваются с списком проблемных МР — это отдельная сущность.

### 4.3. Уведомление в Mattermost

- Если найден хотя бы один проблемный МР — отправляется корневое сообщение в канал (`mattermost.channel_id`) со списком всех найденных проблемных МР по всем репозиториям (формат — см. раздел 6).
- Если в ходе прогона были ошибки:
  - если было отправлено корневое сообщение о проблемных МР — ошибки отправляются реплаем в тред этого сообщения (`root_id` = ID корневого поста);
  - если проблемных МР не найдено (корневое сообщение не отправлялось) — ошибки отправляются обычным (нетредированным) сообщением в тот же канал.
- Если нет ни проблемных МР, ни ошибок — сообщения не отправляются, программа завершается без действий (успешный exit code).

## 5. Конфигурация

Формат — YAML-файл, путь передаётся флагом (например, `--config config.yaml`).

```yaml
gitlab:
  base_url: "https://gitlab.example.com"
  token: "glpat-xxxxxxxxxxxxxxxxxxxx"

mattermost:
  base_url: "https://mattermost.example.com"
  token: "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"   # bot/personal access token
  channel_id: "abcd1234channelid"

check:
  min_reviewers: 2      # по умолчанию 2
  min_age_hours: 24     # по умолчанию 24

repositories:
  - group/project-a
  - group/subgroup/project-b
```

Валидация конфигурации при старте: обязательные поля `gitlab.base_url`, `gitlab.token`, `mattermost.base_url`, `mattermost.token`, `mattermost.channel_id`, непустой список `repositories`. При отсутствии — фатальная ошибка со внятным сообщением до начала работы.

## 6. Формат сообщений в Mattermost

### 6.1. Корневое сообщение (проблемные МР)

```
⚠️ **МР без достаточного количества ревью** (проверка от 2026-07-08 09:00)

**group/project-a** !123 — [Добавить кэширование в API](https://gitlab.example.com/group/project-a/-/merge_requests/123)
Автор: @ivanov · создан 2 дня назад · ревьюеров: 1/2 (@petrov)

**group/project-b** !45 — [Fix flaky test in auth module](https://gitlab.example.com/group/project-b/-/merge_requests/45)
Автор: @sidorov · создан 36 часов назад · ревьюеров: 0/2

Всего найдено: 2
```

### 6.2. Сообщение об ошибках (тред или отдельное сообщение)

```
❌ Ошибки при проверке репозиториев:

• group/project-c: не удалось получить список МР (GitLab API вернул 502)
• group/project-d: превышен таймаут запроса approvals для !78
```

## 7. Архитектура (пакеты)

```
cmd/tf-mr-check/main.go     — точка входа, оркестрация
internal/config             — структуры конфигурации, загрузка и валидация YAML
internal/gitlab              — клиент GitLab API v4: список МР, approvals, notes/discussions
internal/checker             — бизнес-логика: фильтрация draft/возраста, подсчёт ревьюеров, сборка отчёта и ошибок
internal/mattermost           — клиент Mattermost Posts API: CreatePost, CreateReply
```

`main.go` только связывает компоненты (чтение конфига → обход репозиториев → построение отчёта → отправка в Mattermost), не содержит бизнес-логики.

## 8. Логирование

Структурированный лог в stdout (уровень info/error), достаточный для диагностики без включения debug-режима: какие репозитории обработаны, сколько МР проверено, сколько проблемных найдено, какие ошибки возникли. Секреты (токены) в лог не попадают.

## 9. Тестирование

- Юнит-тесты фильтрации draft/возраста и подсчёта уникальных ревьюеров — на моках GitLab-клиента (без реальных сетевых вызовов).
- Юнит-тесты сборки сообщений (формат корневого поста и треда ошибок).
- Моки Mattermost-клиента — проверка, что:
  - реплай с ошибками уходит с корректным `root_id`, когда есть корневой пост;
  - при отсутствии проблемных МР ошибки уходят обычным сообщением без `root_id`;
  - при отсутствии и МР, и ошибок вызовов отправки не происходит.
- Проверка сборки (`go build ./...`).

## 10. Вне рамок (non-goals)

- Не реализуется веб-интерфейс, база данных, хранение истории прогонов.
- Не реализуется собственный планировщик/демон — периодичность задаётся внешним cron.
- Поддержка GitHub/Bitbucket не входит в эту версию.

## 11. Критерии приёмки

1. Бинарник собирается командой `go build ./cmd/tf-mr-check`.
2. При запуске с валидным конфигом и реальным (или тестовым) GitLab-проектом корректно определяет draft МР и исключает их из проверки.
3. Проблемные МР (возраст > `min_age_hours`, ревьюеров < `min_reviewers`) корректно определяются и попадают в сообщение Mattermost.
4. Ошибка на одном репозитории не прерывает обработку остальных.
5. Ошибки уходят в тред под сообщением о проблемных МР, если оно было отправлено; иначе — отдельным сообщением.
6. При отсутствии проблемных МР и ошибок сообщения не отправляются.
7. Юнит-тесты (включая моки Mattermost и GitLab) проходят зелёным.
8. README.md на русском языке актуален и описывает конфигурацию и запуск.
