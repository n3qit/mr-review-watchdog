# mr-review-watchdog

Утилита проверяет заданный список репозиториев GitLab на наличие merge request'ов,
которые открыты более суток **рабочего времени** (выходные и праздники по
производственному календарю РФ не учитываются) и не набрали минимально
необходимое количество ревью. Такие МР публикуются списком в канал Mattermost;
туда же отдельным списком попадают МР, которые ещё не достигли порога
возраста ("молодые"), — для наглядности, что скоро попадёт в проверку.
Ошибки — реплаем в тред под этим сообщением. Бинарник запускается разово (по
расписанию через внешний cron/scheduler), демоном не является.

## Требования

- Go 1.24+
- GitLab EE с доступом к REST API v4 и personal access token с правом на чтение
  проектов, merge requests, approvals, discussions и (если используется фильтр
  по команде) участников группы.
- Mattermost с ботом (personal access token), имеющим право постить в целевой канал.
- Доступ к API производственного календаря РФ — по умолчанию публичный
  [calendar.kuzyak.in](https://calendar.kuzyak.in), аутентификация не требуется.

## Сборка

```sh
go build -o bin/mr-review-watchdog ./cmd/mr-review-watchdog
```

или

```sh
make build
```

## Конфигурация

Конфигурация передаётся флагом `--config` и представляет собой YAML-файл:

```yaml
gitlab:
  base_url: "https://gitlab.example.com"
  token: "glpat-xxxxxxxxxxxxxxxxxxxx"
  team_group: "group/our-team"   # опционально, см. ниже

mattermost:
  base_url: "https://mattermost.example.com"
  token: "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"   # bot/personal access token
  channel_id: "abcd1234channelid"

calendar:
  base_url: "https://calendar.kuzyak.in"   # опционально, это значение и так используется по умолчанию

check:
  min_reviewers: 2      # по умолчанию 2
  min_age_hours: 24     # по умолчанию 24

repositories:
  - group/project-a
  - group/subgroup/project-b
```

Обязательные поля: `gitlab.base_url`, `gitlab.token`, `mattermost.base_url`,
`mattermost.token`, `mattermost.channel_id`, непустой список `repositories`.
При отсутствии любого из них программа завершится с ошибкой ещё до начала
проверки.

`gitlab.team_group` — опциональное поле. Если задано, в проверку попадают
только МР, автор которых является **прямым** участником указанной группы
(участники, унаследованные из родительских групп, не учитываются). Если поле
не задано — фильтрация по команде не применяется, проверяются МР всех
авторов. Ошибка получения списка участников группы фатальна для всего
прогона — программа завершится с ошибкой, не отправив ни одного сообщения.

`calendar.base_url` — опциональное поле, адрес сервера API производственного
календаря РФ. Нужен, только если используется self-hosted зеркало вместо
публичного `calendar.kuzyak.in`.

## Запуск

```sh
./bin/mr-review-watchdog --config config.yaml
```

Периодичность запуска задаётся внешним планировщиком (cron, systemd timer и т.п.) —
собственного демона/планировщика утилита не содержит.

## Логика проверки

Если задан `gitlab.team_group`, перед обходом репозиториев один раз
запрашивается список прямых участников этой группы.

Для каждого репозитория из конфигурации:

1. Получаются все МР в состоянии `opened` (с пагинацией по GitLab API).
2. Исключаются draft МР (`draft == true` или legacy `work_in_progress == true`)
   — такие МР нигде в отчёте не показываются.
3. Если задан `team_group` — исключаются МР, автор которых не входит в список
   участников команды — такие МР тоже нигде в отчёте не показываются.
4. Для оставшихся МР считается количество уникальных ревьюеров — пользователей,
   отличных от автора, поставивших approve и/или оставивших
   комментарий/обсуждение в треде (системные заметки не учитываются; ревьюеры
   вне команды считаются наравне со всеми), — и статус ревью (см. ниже).
5. Если **рабочий возраст** МР меньше `min_age_hours` часов (см. ниже) — МР
   попадает в список "молодых" (со всей посчитанной статистикой ревью).
6. Иначе, если ревьюеров меньше `min_reviewers` — МР считается проблемным.
7. Иначе (МР достаточно старый и ревьюеров хватает) — МР нигде не показывается.

Ошибка при обработке одного репозитория или отдельного МР (недоступен API,
таймаут и т.п.) не прерывает проверку остальных — она добавляется в отдельный
список ошибок.

### Рабочий возраст МР

`min_age_hours` считается не в астрономических часах, а в часах, попавших на
**рабочие дни** — время, пришедшееся на выходные (Сб/Вс) и праздники
производственного календаря РФ, в возраст не засчитывается. Например, МР,
созданный в пятницу в 18:00, при пороге 24ч не станет проблемным в
понедельник в 10:00 (в старой логике на часах — стал бы): за вычетом выходных
прошло всего 16 рабочих часов.

Дни недели и список праздников определяются по московскому времени
(`Europe/Moscow`), список праздников на конкретный год запрашивается у API
[calendar.kuzyak.in](https://calendar.kuzyak.in) лениво (не чаще одного раза
на год за весь прогон) и кэшируется в памяти на время выполнения. Ошибка
получения календаря за нужный год — это ошибка по конкретному МР (попадает
в `report.Errors`, как и прочие ошибки уровня МР), а не фатальная ошибка
всего прогона.

Предпраздничные сокращённые дни (`shortDays` в API) остаются рабочими —
учитываются полностью. Перенос выходного дня на будний день (и обратно —
рабочей субботы взамен) в API отдельно не выделяется, поэтому такие
перенесённые рабочие выходные (несколько дат в год) в расчёте засчитываются
как обычные нерабочие — единственное следствие: МР в это редкое окно может
быть помечен проблемным на день позже, чем формально положено, никогда
раньше.

Запросы к calendar API повторяются до 3 раз при транзиентных сбоях (сетевые
ошибки, 5xx) с небольшой паузой между попытками; ошибки формата запроса
(4xx, например неверный год) не повторяются. Если после всех попыток
получить праздники за нужный год не удалось — это ошибка по конкретному МР,
не всего прогона (см. выше).

Подробное описание алгоритма, разобранная нерассмотренная альтернатива
(точная проверка каждой даты через API) и сравнение — в
[docs/calendar-holidays.md](docs/calendar-holidays.md).

## Статус МР и статистика ревью

Для каждого МР, попавшего в список молодых или проблемных, в отчёт
дополнительно попадают:

- **статус** — один из трёх:
  - `ожидает ревью` — ни аппрувов, ни тредов обсуждения нет;
  - `ожидает исправления` — есть хотя бы один незакрытый code-review тред;
  - `исправлено` — все треды закрыты и/или есть хотя бы один аппрув;
- **аппрувов** — количество approve;
- **тредов** — количество code-review тредов (заметок с признаком
  `resolvable`) и сколько из них закрыто (`resolved`). Обычные комментарии,
  не являющиеся частью резолвящегося треда, в счётчик тредов не входят, но
  их авторы всё равно учитываются как ревьюеры.

Статистика считается одинаково для молодых и проблемных МР — карточки в
обоих разделах сообщения выглядят идентично.

## Уведомления в Mattermost

- Если найден хотя бы один молодой ИЛИ хотя бы один проблемный МР — в канал
  отправляется корневое сообщение. Раздел молодых МР (если есть) идёт первым,
  раздел проблемных (если есть) — вторым; пустой раздел не рендерится вовсе.
- Если в ходе прогона были ошибки:
  - при наличии корневого сообщения (молодые и/или проблемные МР) — ошибки
    уходят реплаем в его тред;
  - если ни молодых, ни проблемных МР не найдено — ошибки уходят обычным
    сообщением в канал.
- Если нет ни молодых, ни проблемных МР, ни ошибок — сообщения не отправляются.

Каждый МР — отдельный пункт маркированного списка. Пример корневого
сообщения (есть и молодые, и проблемные МР):

```
🕒 **МР, которые скоро попадут в проверку**

- **group/project-c** !88 — [Fix typo](https://gitlab.example.com/group/project-c/-/merge_requests/88)
  Автор: @sidorov · создан 2 часа назад · статус: ожидает ревью
  ревьюеров: 0/2 · аппрувов: 0 · тредов: 0 (исправлено 0/0)

Скоро попадёт в проверку: 1

⚠️ **МР без достаточного количества ревью**

- **group/project-a** !123 — [Добавить кэширование в API](https://gitlab.example.com/group/project-a/-/merge_requests/123)
  Автор: @ivanov · создан 2 дня назад · статус: ожидает исправления
  ревьюеров: 1/2 (@petrov) · аппрувов: 0 · тредов: 3 (исправлено 1/3)

Всего найдено: 1
```

## Архитектура

```
cmd/mr-review-watchdog/main.go   — точка входа, оркестрация (без бизнес-логики)
internal/config           — структуры конфигурации, загрузка и валидация YAML
internal/gitlab           — клиент GitLab API v4: МР, approvals, discussions, участники группы
internal/calendar         — клиент API производственного календаря РФ: праздники по году
internal/checker          — фильтрация draft/возраста/команды, подсчёт ревьюеров и статуса, отчёт
internal/mattermost       — клиент Mattermost Posts API: CreatePost, CreateReply
```

## Тестирование

```sh
go test ./...
```

или

```sh
make test
```

Юнит-тесты покрывают:

- фильтрацию draft/команды, подсчёт уникальных ревьюеров, вычисление статуса
  МР и бакетирование в молодые/проблемные (`internal/checker`, на моках
  GitLab-клиента);
- расчёт рабочего возраста МР: одни сутки без выходных, охват выходных,
  охват праздника, ошибка календаря — не фатальна для всего прогона, кэш
  запрашивает праздники года не более одного раза (`internal/checker`);
- сборку текста корневого сообщения (оба раздела, только молодые, только
  проблемные, оба пустых) и сообщения об ошибках (`internal/checker`);
- клиенты GitLab, Mattermost и календаря, включая `ListDiscussions`,
  `ListGroupMembers` и `GetHolidays` с ретраями (успех после 1-2 неудач,
  ошибка после исчерпания попыток, отсутствие ретрая на 4xx)
  (`internal/gitlab`, `internal/mattermost`, `internal/calendar`, на `httptest`);
- оркестрацию отправки в Mattermost (`cmd/mr-review-watchdog`, на моках): реплай с
  корректным `root_id`, обычное сообщение без `root_id` при отсутствии
  молодых/проблемных МР, отправку сообщения только по молодым МР без реплая,
  отсутствие вызовов при отсутствии МР и ошибок, фатальную ошибку получения
  списка участников команды и нефатальную ошибку календаря.

## Логирование

Структурированный (JSON) лог в stdout на уровнях info/warn/error: сколько МР
получено на репозиторий, сводка по репозиторию после обработки (сколько
draft, не из команды, молодых, проверенных, проблемных), получение списка
команды, попытки запроса к calendar API при ретраях, отправка каждого
сообщения в Mattermost. Токены в лог не попадают.
